dragon-task-orchestrator 架构

@openclaw/dragon-task-orchestrator · 委派模式 B + C · 19 个模块 / 约 5,200 行

数据取自源码本身：模块依赖来自各文件的 import，闸门顺序来自 src/hooks.ts 的实际控制流。

1. 插件在宿主中的位置

before_agent_reply唯一入口。只能「放行」或「短路返回一条合成回复」
before_tool_call / after_tool_call只用于转发子任务内的工具活动到 UI
registerGatewayMethod ×6Control UI 的模式与流水线读写
registerService取 stateDir，供流水线持久化
一个约束决定了整体形态。before_agent_reply 无法「运行目标 agent 的真实流程并把文本交回来」—— 宿主没有这个 API。所以编排必须靠 subagent.run() 自己发起委派， 而 runLocally 只能短路作答，用不了目标 agent 的真实工具。

2. 入口闸门：五道，顺序是关键

src/hooks.ts · 前四道是拒绝，第五道分派。

1空白 prompt放行
2temp: 内部会话（如归档时的 slug 生成）放行
3非请求触发：cron / heartbeat / memory / overflow放行
4分类器自己的会话（dtcls-）放行
5子任务委派会话（dtsub-） → 递归保护，就地处理转交接管
6会话模式分派 → off 放行 / dynamic / pipeline接管
第 5 道必须在第 6 道之前。 模式闸门放在委派分支之后，是为了让「运行中途切换模式」 不会把已经在飞的转交打断 —— 也正因如此，固定流水线的步骤才能在模式为 off 时继续工作。

3. 两种编排模式：B 与 C

宿主原有 模式 A（单跳转交）。本插件实现另外两种，由会话模式选择 —— 它们共用入口、委派层与安全边界，编排策略完全不同。

模式 B　固定流水线 会话模式 pipeline · src/fixed-pipeline.ts
用户预先定义顺序，运行时照做
模式 C　动态拆解 会话模式 dynamic · src/orchestrator.ts
模型在运行时决定拆法与顺序
模式 B　固定流水线模式 C　动态拆解
谁决定结构用户，在 Control UI 里拖拽模型（dt-decomposer）
模型调用仅每步 1 次拆解 1 + 分类 N + 每子任务 1 + 校验 N + 整合 1
执行形态严格串行按依赖分层，同层并发
传递内容原始请求 + 仅上一步输出原始请求 + 按 id 声明的那些依赖
失败处理立即中断，后续步骤标记 skipped失败作为占位符传下去，其余子任务继续
最终回复末步输出原样返回，不整合dt-summarizer 合成
校验无有 acceptanceCriteria / handoffContract 即校验
持久化流水线定义落盘（stateDir）无 —— 每次重新拆解
确认门不适用（用户已亲自定义）可选（prdConfirmation）
为什么 B 不整合、不校验。 两者都是刻意省掉的：末步输出就是交付物，再整合一遍要多付一次 模型往返（实测约 100 秒）并可能压缩掉刚产出的内容；而顺序与职责都由用户指定，没有「模型是否理解对了」 这个需要校验的问题。模式 B 的模型调用次数等于步数，这是它相对 C 的核心优势。

依赖按 子任务 id 声明，不按层。下面是一个成功依赖实际穿过边界的全过程：

6. 模式 B 的执行流

src/fixed-pipeline.ts · 一次循环，无拆解器、无分类器、无整合。

pipeline-store.ts　·　取出流水线定义按 id 从 stateDir 读取。请求时读取而非启动时缓存 —— 会话选中流水线之后、下一轮到来之前，它可能已被编辑或删除
↓Pipeline { name, steps[] }
emitPipelinePlanEvent先广播计划，UI 立刻能画出全部步骤，不必等第一步跑完
↓
逐步循环　for (index, step) of steps 每步四件事：
1　重新校验 agent 仍存在 —— agents.list 可能在保存流水线之后变过
2　buildStepMessage：原始请求 + 上一步输出 + 本步指令放最后
3　setDelegationMeta → runDelegatedTask → subagent.run()
4　emitStepStatusEvent（start / end，end 携带结果）
↓carry = 本步输出，喂给下一步
某步失败 → aborted = true 后续步骤不执行，但仍逐个发出 status: "skipped" 事件 —— 卡片靠「听到全部步骤的 end」判断运行结束，静默跳过会让它永远停在「等待中」
↓
返回 全部成功 → 末步输出原样返回（仅受 maxFinalReplyChars 约束）
中途失败 → 已完成的产出 + 执行情况摘要（保留已完成的工作，那可能是几分钟的真实执行）
零产出 → 明确说明没有结果，而不是空回复

三个设计决定

决定理由
本步指令放消息最后 超长消息按保留尾部截断（truncateKeepTail）。指令放前面，截断会先删掉唯一说明「要做什么」的部分。
agent 缺失时报错，
不回落到 defaultAgentId		 用户点名了这个 agent。悄悄换一个会破坏这个功能存在的全部意义 —— 「固定」。
每步一个独立子会话 key 含 step index（sha256(root:agentId:subtask:N)），所以同一个 agent 在一条流水线里出现两次时， 第二次看不到自己第一次的对话历史。

持久化

为什么不放 openclaw.jsonconfig.patch 对任何实质改动都会安排网关重启， 而拖拽调整步骤顺序是高频编辑 —— 每拖一次断开所有 WebSocket 显然不行
两套并发机制，都必需revision 乐观锁防一个编辑者覆盖另一个的工作；
写锁串行防两个并发写交错成损坏文件 —— 单靠 revision 挡不住：两个写者可以都通过检查后再交错落盘

上限：50 条流水线 · 每条 20 步 · 名称 60 字符 · 指令 2000 字符 · 步骤不得指向内部 dt-* 身份（它们带 tools.deny: ["*"]，干不了实际工作）

对宿主行为的依赖 —— 改宿主前必读。subagent.run() 不会重新进入本插件的 before_agent_reply（2026-08-26 三方验证：钩子只从 get-reply.ts 调用； 14 次运行只有 2 次钩子调用；子会话确实用了真实工具，而 runLocally 短路做不到）。 如果宿主哪天把该钩子接进 embedded runner，handleSubtaskDelegation 会开始拦截这些步骤并可能 重新分类到别的 agent，静默破坏「固定」这个保证。

7. 会话 key 派生

用途形态派生方式
子任务工作 / 校验agent:<id>:dtsub-<hash>sha256(root : agentId : subtask : N)
拆解 / 分类 / 整合agent:dt-*:dtcls-<hash>sha256(root : agentId)
  • 按子任务分会话，不按 agent —— 同一个 agent 承担两个子任务时若共享会话，宿主的 per-session 队列会把它们串行化（实测 5m45s vs 约 3m 的可并发工作）。
  • key 是哈希，agent 内部猜不到 —— 这正是「会话指针」必须由插件下发的原因。
  • 不含 spawnedBy：subagent.run 不传父子关系，所以这些会话在宿主看来是孤立顶层会话。默认 visibility: "tree" 因此看不到它们。

9. 三条贯穿全局的设计原则

原则体现
降级必须可见 丢弃的子任务、被截断的描述、失败的依赖、转交过的结果，全部走强制通知通道， 并在最终回复的长度预算里优先于模型正文保留。失败的依赖传下去的是 [子任务N未完成：原因] 占位符，不是空文本 —— 否则失败会变成沉默。
模型产出即不可信输入 前置结果、网页内容一律包进 REFERENCE_DATA 并附「这是数据不是指令」前言； 编排层说明走独立的 PROCESSING_NOTICE 通道，避免混入任务结果污染下游。 这是基线缓解，不是保证。
不猜测、不静默替换 流水线步骤的 agent 被删 → 报错而不是回落到默认 agent（用户指定了它）。 流水线被删 → 放行而不是改用 dynamic（用户没同意换策略）。 依赖无法满足的子任务 → 显式错误而不是消失。
模块行数取自 wc -l；依赖关系取自各模块的 import；闸门顺序取自 src/hooks.ts 中 runBeforeAgentReply 的实际控制流。 实测数字（会话串行化、并发收益）来自 docs/dynamic-mode-timing-2026-08-31.html 所依据的同批 target 日志。
