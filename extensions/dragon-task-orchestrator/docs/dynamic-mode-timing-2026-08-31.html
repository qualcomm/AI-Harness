元凶已点名

本轮新增的 per-provider 探针给出了确切归属。探测已经并发（上限 8），所以一个 order 的耗时等于它最慢那个供应商的耗时：

catalog order=simple  14982ms
  └─ probe simple/amazon-bedrock-mantle  14977ms   ← 几乎等于整个 order

超过 5 秒的探测，全部出现次数：
  7 ×  simple/amazon-bedrock-mantle   （14.2s ~ 25.0s）
  2 ×  late/lmstudio                  （最高 14.5s）
  1 ×  late/ollama                    （10.3s）

其余 30 余个供应商全部 ≤ 4.4s
  anthropic-vertex 4372ms · litellm 4398ms · qwen 4098ms · deepseek 4372ms …
根因：非 live 模式下探测完全没有超时。 resolveLiveProviderCatalogTimeoutMs 在非 live 模式返回 null， 所以一个连不上的供应商想等多久就等多久。上面三个都没有配置凭证 —— 探测注定失败， 只是失败得很慢。

为什么缓存只能到这里

catalog memo 命中 2 次、未命中 7 次。7 个不同的 key 对应 7 个 agent （coding / research / writing / dt-decomposer / dt-classifier / dt-summarizer + main）。

这 7 个 key 是正确的，不是缺陷。 agentDir 必须在 key 里 —— 凭证按 agent 隔离 （auth-profiles.json 是 per-agent），不同目录确实可能得到不同的目录结果。 要压到 1 个 key 就得假设「所有 agent 凭证相同」，那是用正确性换速度。 缓存这条路已经走到头，剩下的收益在超时。

4. 第 2 层占了一半时间

420.7 秒里，382.2 秒是子任务 2（writing）自己的工作，启动开销只有 4ms（缓存命中）。 这一段不是开销，是真实工作：7 次 exec、3 次 read、1 次 edit， 最终写出 12.3KB 文档。

前几轮的改动在这里见效了。 maxContextChars 2000→16000 与 handoffContract 落地后： 子任务 2 自发 web_search 次数为 0（基线 5 次）， 上下文溢出 0 次（基线 1 次 48s 压缩），校验重试 0 次（基线 1 次）。 它拿到了依赖的资料，不再重做上游的工作。
