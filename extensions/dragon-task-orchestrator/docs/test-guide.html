1. 插件是什么

这是一个 OpenClaw 插件：当用户的一句话请求实际上包含多个子任务（例如"帮我搜集资料、算路线、再写成一篇攻略"），插件会把它拆成若干子任务，分别派给合适的 agent 执行，处理依赖关系，最后把结果汇总成一条回复。

默认关闭。插件注册的一切（钩子、网关方法）只在 enabled: true 时生效；即使插件开着，每个会话仍需要显式选择模式才会触发任何行为——不选就是纯粹的旁路（passthrough）。

2. 三种会话模式

模式是按会话设置的，只存在内存里，重启网关会清空（这是有意为之，不是 bug——见第 7 节）。

模式行为
off（默认）原样放行这一轮，插件完全不介入。
dynamic拆解 → 路由 → 分层执行 → 校验 → 汇总。测试重点。
pipeline运行用户预先配置好的固定 agent 顺序，没有拆解器、没有分类器。

3. Dynamic 模式的执行流程

① 拆解
decomposer 把请求拆成带 description / acceptanceCriteria / handoffContract / needsPriorResults 的子任务。少于 2 个存活子任务 → 直接放行不拆。
② 路由
classifier 给每个子任务单独选一个目标 agent。
③ 确认（可选）
开启 PRD 确认门后，2+ 子任务的拆解方案会先在 Control UI 展示，等待"确认/取消/调整"。
④ 分层执行
按 needsPriorResults 做拓扑排序。同一层内的子任务并发执行，层与层之间是屏障（barrier）。
⑤ 校验
带 acceptanceCriteria 或 handoffContract 的子任务由独立的 verifier 判定，不通过则重新委派，上限 maxVerifyRetries 次。
⑥ 汇总
summarizer 把所有子任务结果整合成一条最终回复。

子任务之间怎么传数据（这是最容易出问题的地方）

下游子任务能看到的，只是它依赖的上游最终一条回复正文——看不到工具调用过程，看不到中间步骤，正文超过 maxContextChars（默认 16000 字符）的部分会被截断。为了让这条窄通道够用，有三条并行的机制：

机制作用
handoffContract 一份清单，列出上游正文必须包含的具体条目（某个数字、某个来源）。漏项会被校验判不通过，而不是悄悄放过。
共享产物目录 近期修复 有下游依赖的子任务会拿到一个绝对路径目录（<stateDir>/artifacts/<hash>/subtask-N/），可以把完整产出写进去；下游拿到的是扫描出来的真实文件绝对路径。
会话指针 每个依赖的正文后面附带它的子会话 key，需要完整细节可以用 sessions_history 读取。需要宿主开 tools.sessions.visibility: "all" 和 tools.agentToAgent.enabled，任一没开就会被拒绝。

4. 如何开启和配置

4.1 最小配置

{
  "plugins": {
    "allow": ["dragon-task-orchestrator"],
    "entries": {
      "dragon-task-orchestrator": {
        "enabled": true,
        "config": {
          "enabled": true,
          "defaultAgentId": "coding",
          "logging": true,
          "agentDescriptions": {
            "coding": "代码相关，以及任何涉及本地文件系统的任务",
            "research": "网络搜索与外部资料核查，需带引用",
            "writing": "面向读者的成文：文档、指南、报告"
          }
        }
      }
    }
  }
}

完整参考配置（含三个内部 agent 的 systemPromptOverride 全文）见 docs/openclaw.json。

4.2 三个必须存在的内部 agent

宿主的 agents.list 里必须有以下三个身份，每个都要用 systemPromptOverride 承载完整指令、并 deny: ["*"] 禁掉全部工具：

dt-decomposer把请求拆成子任务
dt-classifier把一条子任务描述分类到一个 agent id
dt-summarizer汇总出最终回复

4.3 打开某个会话的 dynamic 模式

模式是运行时通过网关方法设置的，不是写死在配置文件里：

dragonTaskOrchestrator.session.mode.set  { sessionKey, mode: "dynamic" }

或在 Control UI 里为该会话选择 dynamic 模式。切换会话 / 重启网关都会回到 off，需要重新设置。

4.4 启动网关并抓日志

cmd /c "node openclaw.mjs gateway run --verbose > gateway.log 2>&1"

4.5 一个可以直接用的测试 prompt

将我的任务拆分为多个子任务。我计划国庆去河西走廊，你帮我搜索河西走廊的资料，
我需要自驾从成都出发，输出一个合理的旅游攻略文档。

这个 prompt 天然会拆成 research + writing 两类子任务、带依赖关系，能覆盖第 3 节的全部机制。

5. 如何观察一次运行

5.1 关键日志行（logging: true 时）

[dragon-task-orchestrator] decomposition validated on <session>: N surviving subtask(s)
[dragon-task-orchestrator] pipeline on <session>: N subtask(s) resolved to [0:research, 1:writing], M layer(s)
[dragon-task-orchestrator] layer 1/2 on <session>: N subtask(s) in parallel
[dragon-task-orchestrator] subtask 0 on research: ok
[dragon-task-orchestrator] summarizing N subtask result(s) on <session>: N ok, 0 failed

出现 subtask N on <agent>: verify failed 或 经 Verifier 校验 N 次未通过 说明校验环节在起作用，不是异常。

5.2 Control UI 的进度事件

以 plugin_event 广播，type: "dragon_task_progress"，按 kind 区分：

prd拆解方案（先发结构，路由结果出来后再发一次）
subtask_status某个子任务开始/结束
subtask_tool子任务内部的一次工具调用（含压缩后的摘要）
layer_progress一层执行完毕及其结果
summarizing全部子任务结束，正在汇总

5.3 判断产物通道是否生效

在日志里搜 artifacts 或 共享产物目录，正常情况下应该能看到类似：

write: path=C:\Users\...\.openclaw\artifacts\<hash>\subtask-0\xxx.md
read:  path=C:\Users\...\.openclaw\artifacts\<hash>\subtask-0\xxx.md

关键判据：写入的路径和下游读取的路径必须是完全同一个绝对路径，且不应出现 ENOENT。

6. 常见的"看起来像 bug 但不是"的现象

正文里出现内容被截断的提示 形如"内容过长，已截断 N 字符"。这是插件为控制上下文预算主动做的处理，不是模型输出不完整或程序出错。校验器也被明确告知不能因为这个提示判定失败。
web_fetch 报 499 且带一段"SECURITY NOTICE"文字 这不是网络故障，是宿主的抓取安全防护判定目标页面内容可能构成提示词注入而主动拒绝返回。agent 通常会自行换一个信息源继续。如果这类拒绝频繁出现且阻塞了任务，值得记录下具体 URL，但单次出现且被绕过不算异常。
校验失败后子任务被重新委派、正文里出现"经过 N 次校验通过" 这是校验环节按设计工作的证据，说明 handoffContract / acceptanceCriteria 真的在被强制执行，不是流程卡住或重复执行的 bug。
同一层里两个子任务的日志时间线交织在一起 同层子任务是并发执行的，日志会交叉打印，这是预期行为。判断是否真正并发，看时间戳是否有重叠，而不是看日志顺序是否"整齐"。
